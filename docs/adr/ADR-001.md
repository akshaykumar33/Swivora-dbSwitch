# ADR-001: Selection of Monorepo Architecture and Turborepo Build Pipeline

## Context & Problem Statement

MorphDB is designed as an enterprise open-source database abstraction layer comprising multiple independent NPM packages: core orchestrators, schema IR engines, query builders, AST compilers, and database adapters. We need a repository architecture that supports independent package publishing, rapid local development iteration, shared linting/testing configurations, fast incremental builds, and strict dependency isolation.

---

## Decision Drivers

- **Modularity**: Users using `@morphdb/adapter-postgres` must not pull in MongoDB BSON drivers or unwanted packages.
- **Developer Velocity**: Running tests or builds across 15+ packages must leverage incremental parallel execution and build caching.
- **Type Safety**: Cross-package imports within the repository must instantly reflect TypeScript type updates without requiring manual publishing.

---

## Technical Options Evaluated

### Option 1: Multi-Repository Layout (Separate GitHub Repositories per package)
Each package (`@morphdb/core`, `@morphdb/schema`, `@morphdb/adapter-postgres`) gets its own GitHub repository.
- *Pros*: Completely isolated CI pipelines and permissions.
- *Cons*: Nightmare cross-repo coordination for breaking refactors across core and adapters; dependency version drift.

### Option 2: Monorepo with `pnpm` Workspaces and `Turborepo` (Selected)
A single repository containing `packages/`, `adapters/`, `apps/`, and `examples/`.
- *Pros*: Symlink dependency resolution, content-addressable storage, strict package hoisting isolation, parallel topology builds, and local/remote build caching via Vercel.
- *Cons*: Requires strict configuration of monorepo root settings.

### Option 3: Monorepo with `Nx`
- *Pros*: Advanced code generators and dependency graph visualizers.
- *Cons*: Heavy abstraction layers and complex plugin ecosystems that conflict with our zero-magic philosophy.

---

## Decision Outcome

**Selected Option**: **Option 2 (Monorepo with pnpm Workspaces & Turborepo)**.

---

## Rationale & Tradeoffs Analysis

### Why pnpm + Turborepo?
1. **Speed & Efficiency**: `pnpm` reduces disk consumption by hard-linking packages, while `Turborepo` caches previous build and test outputs using SHA-256 hashes of input files.
2. **Strict Package Boundaries**: `pnpm` prevents phantom dependencies (importing a package that is not explicitly declared in a package's `package.json`).

### Tradeoffs
Requires workspace protocol references (`"workspace:*"`), which must be resolved to semver numbers during release publishing via `Changesets`.

### Future Scalability
Adding new official database adapters (e.g. `@morphdb/adapter-redis`, `@morphdb/adapter-sqlite`) requires adding a folder under `adapters/` without disrupting existing packages.
